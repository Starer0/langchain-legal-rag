# 模型驱动的意图识别与统一记忆工具：设计草案

状态：2026-10-08 已按本设计完成实现、程序验证和本地部署；用户统一验收待进行。实测记录与限制见 docs/v12-19-model-memory-tools.md。

执行偏好补充：用户随后允许将整项升级连续完成，不需要内部每个小Task都停下交给用户验收。保持关键解释与进度，完成整体实现和必要程序验证后统一用户验收；当前实现已完成，未代用户操作真实记忆做验收。

本稿替代 memory-consolidation-design.md 的三个固定风格维度设计。结论先行、分点、例子仅作为回归样例，不限制模型可以发现的偏好、稳定背景与近期学习主题。沿用 PostgreSQL、核心/扩展记忆、来源保护和当前对话逐步实施方式，不引入 Letta SDK 或独立网关服务。

## 目标和职责

前台：用户输入 → 模型结合上下文理解意图 → 提出记忆工具调用及回答路线 → 程序验证、提交 → 返回实际结果。

后台：服务器按现有空闲/压缩策略启动 → 模型回顾原始用户消息与已有记忆 → 提出更新或不操作 → 同一个记忆工具提交。

语义判断交给模型：是否有持续偏好、是否明确要求保存、与已有内容是否重复/补充/矛盾。工具负责数据边界：账号、开关、来源位置、合法操作、版本、预算、事务和幂等。不能宣称程序检查出处就能证明语义归纳正确；误判率通过评测观察。

## 前台模型怎样看到意图

取消 web_intent.py 的关键词白名单作为新网页路径的分流门槛，也取消 command_candidate 作为进入模型的必要条件。历史CLI或旧模块如仍使用旧函数，保持独立兼容，不为了本次升级改全仓库。

上下文准备后新增 understand 节点，每条新消息都进入模型。模型输入包括当前原文、有限近期用户历史、带来源的上下文摘要、冻结记忆及服务端开关。近期历史同时保留原始片段以便判断“以后也这样”之类指代，不能只给法律改写所用的历史。

该节点使用原生 tool calling，暴露两个有界工具：

1. `plan_answer`：每次必须调用一次，纯数据工具，输出 route（rag/preference/general/clarify/out_of_scope）、法律子问题及 retrieval_question/include_guide、简短非法律回复计划、是否存在明确memory_request。
2. `update_memory`：可选，最多一次，参数是至多12项更新。与 plan_answer 同一次模型响应返回；不能直接输出SQL、user_id或数据库连接。

模型能力测试必须验证当前供应商能在一次响应输出这两个调用。缺少/重复plan_answer、重复update_memory、未知工具或参数不合法时不执行记忆写入，给出可重发/设置编辑的反馈；不静默退回关键词，不启动无限工具循环。标准路径一次understand调用，无独立“先分类再改写”调用。

rag路线复用understand给出的检索改写，跳过原网页rewrite模型调用；保留rewrite等价字段和已有资料范围/指南选择校验。检索范围由服务器生成，模型不能扩大。纯偏好/记忆请求不检索法律；一般寒暄或产品说明不附法条，具体法律结论必须经过RAG。

理解与后台回顾保留授权原始消息；法律摘要按持久route过滤纯偏好/记忆命令，混合消息仅使用legal_question。新路径不再依赖关键词过滤历史。旧消息没有route时保留兼容过滤，不为迁移全量调用模型。

支持混合意图：如“以后先给结论；试用期最长多久”，同时提出更新和法律路线。保存失败或被阻止也不应丢掉已完成的法律回答。临时要求影响当前回复，不写长期记忆。

## 工具参数与实际执行

`update_memory` 的动作是 remember/merge/propose_change/request_delete/request_clear。remember可用任意简短文字描述稳定偏好/背景；没有固定的answer.order等含义白名单。每个候选包含：

- content：原子含义的归纳文字，一条尽量只表达一个可独立更新的事实。
- layer：core/extended；category：preference/background/learning_focus（存储分类，不限制具体话题）。
- basis：declared/inferred；source_refs：原文摘录和来源定位。
- target_ids：重复/补充/冲突所针对的现有条目id。
- relation：new/duplicate/complement/conflict；delta：补充关系中的新增含义。

调用者不能自报权限。服务端绑定 owner、任务、来源、revision和policy_epoch；模型只提供引用。前台明确更新需plan_answer的memory_request与当前用户原文相符；自然表达只是当前偏好回应时，后台积累仍受自动开关控制。明确新增不依赖自动积累开关；关闭自动不阻止用户手动编辑或明确要求保存。若请求含糊，转建议/澄清。语义是否明确由模型判断，有误判可能，需专门测量“把普通表达误当保存命令”的比例。

不让模型以 inferred 标记自动创造确定画像：间接学习主题初期一律待用户确认，放扩展层。后台不能删除/清空/替换手动段落。明确删除或清空只生成确认请求，用户通过已认证界面确认后执行；普通新增与有证据的重复合并不逐条打断用户。

沿用现有事务边界：前台工具执行分为准备和提交，prepare生成待提交变更，generation complete事务中正式执行并写入用户/助手消息和工具结果；后台在原job apply事务中执行。模型侧调用是原生tool call，程序不是在普通回复文本里猜“它想保存”。工具内部采用两阶段执行以适配已有消息事务，不向模型或用户提前声称saved。

前台纯记忆回复在提交后依据工具结果生成固定确认，混合问答保留法律回答并单独显示记忆结果；不为确认再调用一次模型。若事务前失败，记忆不写；如果提交后连接断开，重连读取持久结果。记忆冲突/预算失败通过savepoint隔离并记录conflict/blocked，不把成功的法律回答整体作废。

## 开放含义怎样去重

模型一次看到有id的当前条目，与新证据一起判断关系；程序不靠“出现某词”判同义，也不靠向量分数直接覆盖。

- duplicate：已有文字不变，只追加新证据；重复调用同一来源不追加重复证据。
- complement：原条目保留，新增delta作为独立条目并建立补充关联；只有原子内容完全重复时归duplicate，不能把含新信息的整句当重复丢掉。
- conflict/propose_change：产生前后对照建议，确认再替换；自动任务不覆盖用户编辑。
- remember：新增独立条目；渲染成可编辑的段落文本，不使用三种固定模板。

截图中的“先给结论”归duplicate，“结合例子”“分点解释”各自保留。第一版优先保留完整含义，可显示为三个简短条目；整段润色是建议而非自动大范围重写。模型可能错误声明duplicate，来源齐全也无法在程序内证明同义，因此保留被判重复的候选文字及证据供检查，测试新增信息遗漏率。

手动编辑以用户完整文档为准。未改段落保留条目/来源，新增段落登记manual_document，删除条目退休；自动合并不能重写受保护段落。旧文本迁移登记legacy_document，不制造聊天证据、不自动改写用户现有重复数据。

## 后台回顾与画像候选

服务器维持空闲120秒（从最新完成回答起）或上下文压缩触发；浏览器关闭不是“对话结束”的可靠信号。不每问执行一轮后台分析，新问题推迟未开始任务，当前回答有优先权。

每批一次模型回顾，直接产出update_memory调用或不调用；不先生成摘要再调用第二个分类模型。输入仍包含待处理用户原文、至多1000估算token的前文、冻结已有记忆和未处理建议；原文与摘要区分标注，助手说法不作用户事实。

声明式偏好/背景可按策略自动保存。间接推测的学习主题至少引用两个不同用户轮次，只创建建议；两个轮次仅是最小证据门槛，不意味着反复问两次就确定画像。候选可以根据后续证据合并，但不把助手回复、否定、假设或案件内容计为支持证据。首版不跨全量历史反复扫描，也不声称已具备自动长期职业画像。

后台工具允许“不更新”；建议忽略或删除后保留来源失效边界，旧任务不能再造相同记忆。新明确保存可重新授权。近期主题先经用户确认，不加未讨论的自动过期规则；后台推测的期限与置信度研究单列，不能把“近期”永远解释为当前事实。

## 存储、来源与恢复

新增PG条目、证据、工具回执和前台决策表，所有行绑定owner。证据含source_kind、任务或对话定位、原文、时间；前台原文先从已持久generation输入核验，完成事务关联到真实消息序号。不能要求尚未落库的消息已存在，也不能接受模型虚构序号。

工具执行id由服务器从任务/job及操作槽位生成；同一次持久模型决策重放不重复写。回执及版本、条目、向量、文本在原事务内提交。前台决策冻结并随checkpoint保存可序列化内容；运行时模型、存储连接、权限不进入checkpoint。恢复使用同一工具参数，不重跑模型生成不同的删除或更新。

理解前原文日志默认私有，路线确定后只记录legal_question的RAG链路。工具日志记录动作/状态/耗时等元数据，不输出完整记忆原话。后台每项新候选至少有本批未失效来源，不能借前文摘要让用户已删除的记忆复活。

保持现有锁顺序，各流程分别延续现有task/conversation或conversation/user/job顺序，工具不再申请相反顺序的锁。revision或epoch变化使旧提案失效；后台旧任务作废，不无条件覆盖。旧图版本明确终结或沿旧代码兼容路径完成，不能重解释旧memory_result。修改图版本并显式迁移，启动不自动DDL。

来源仅本人可读；删除对话后保留已保存记忆及摘录，取消已失效消息定位，并在界面说明。删除账号清除其条目、摘录、回执。退休记录/被忽略候选只保存防重放所需标识与策略边界，不额外留下已要求删除的完整内容。

## 成本、预算与评测

- 前台每条输入一次understand，RAG复用改写结果；不能保证与原调用数完全相同，纯偏好原本0次现在1次。
- 后台每批一次回顾，正常执行工具不再调用模型；无自动模型重试，无无限循环。
- 保留核心500估算token/1500字符、扩展12000字符/40段/每段1000字符、相关检索最多3段/500估算token。核心不向量化，扩展仅变化时更新向量。
- 前台理解总提示遵守现有PromptBudget，原始近期历史最多1000估算token；core全量、扩展条目在12000字符上限内纳入决策，再作总预算检查，过长要求缩小/编辑，不默默丢掉候选目标。
- 后台新来源4000估算token、前文1000，保持当前后台90秒上限；前台理解初版20秒上限，超时明确失败且不保存，参数可配置，不把它写成已实测最佳值。
- 评测分别记录意图识别、工具参数/调用、重复/遗漏/无依据画像、越权/开关/手动覆盖、调用数/token/时延；夹具成绩与真实模型成绩分开，未测量不写提升百分比。

本轮只写规划，未修改代码、迁移数据库、重启服务、调用真实模型、修改用户记忆或提交推送。用户自己进行验收；助手不能代保存、清空、重试来“通过验收”。
