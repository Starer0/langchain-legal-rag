# V7 复合问题拆分实验

## 运行方式

`python main.py --decompose` 启用复合问题拆分。每轮先沿用 V6 的
History-aware Query Rewrite，再让模型输出 1～4 个独立检索问题。
一个问题时继续原有链路；多个问题时分别执行 Chroma Top 8 和
SiliconFlow Reranker Top 5，按子问题交替选取、去重，最多向最终回答提供 5 条法条。
最终模型只回答用户原始问题，终端显示拆出的子问题。

`python run_composite_baseline.py --decompose --run-id <唯一名称>`
可按独立会话运行 `evals/composite_question_cases.json` 的 8 道题。
原始逐题结果保存在被 Git 忽略的 `evals/results/<run-id>/`。

## 与单查询 Top 5 基线比较

单查询基线 `v7-composite-top5-baseline`：候选 4/8，最终来源 4/8。
初版拆分 `v7-composite-decomposed-top5`：候选 7/8，最终来源 6/8。
聚焦法律术语 `v7-composite-decomposed-top5-prompt2`：候选 8/8，最终来源 5/8。
加入必要前提问题 `v7-composite-decomposed-top5-prompt3`：候选 8/8，最终来源 6/8。

最终版本在这 8 道题上将候选完整覆盖从 4/8 提升到 8/8，
最终来源完整覆盖从 4/8 提升到 6/8。三道普通单问题的真实模型抽查均只返回
一个检索问题，因此会沿用单查询链路。

剩余两题：试用期辞退题的《劳动合同法》第四十六条，以及四法律点综合题的
《劳动法》第四十四条，均已进入候选，但未进入最终五条来源。
当前按子问题轮流取法条的合并方式仍会被语义相近、却不足以支撑回答的条文占位。

## 使用边界

拆分模式目前通过 `--decompose` 显式启用，普通 `python main.py`
仍使用已评测的单查询链路。此次评分只统计法条来源覆盖，没有对每份最终回答
做完整法律准确性评审。资料中《劳动法》第八十二条的“六十日”和
《劳动争议调解仲裁法》第二十七条的“一年”同时可能进入上下文；
曾有一次漏掉第二十七条的实验回答直接引用“六十日”。
因此，来源覆盖提高还不足以支持默认启用。后续应评测证据选择与冲突处理，
再决定是否作为默认方案。
模型生成的子问题有时会写入原问题未提及的法律数值；子问题仅用于检索，
不能视作法律依据，最终回答仍须以检索到的原文为准。
