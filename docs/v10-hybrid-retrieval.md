# V10：混合检索实验

## 要解决的问题

原系统只使用 Chroma 向量检索。它擅长理解相近说法，但法律问答中还存在大量需要精确匹配的内容，例如法条号、期限、金额和专有名词。

本版本在召回阶段增加本地 BM25。它不取代向量检索，而是补充候选资料，最终仍由同一个 Reranker 统一排序。

## 数据流

```text
改写后的检索问题
├─ Chroma 向量召回：默认 8 条
├─ BM25 关键词召回：默认 8 条
│   └─ 两路使用相同的 metadata 范围过滤
├─ 合并并按法条或指南小节去重
└─ Reranker 选出最终 RERANK_TOP_N 条资料
    └─ 回答模型依据这些资料作答
```

因此，启用混合检索不会增加回答模型或 Reranker 的调用次数。

## BM25 在此项目中的实现

`bm25_retriever.py` 在打开已经发布的 Chroma 知识库后，读取其中已有的文本和 metadata，在内存中建立倒排索引。它不会重新读取 PDF，也不会调用 Embedding API。

中文文本没有天然的空格分词。为保持依赖最少，本项目把连续中文文字切为二字词片段。例如“试用期工资”会产生“试用”“用期”“期工”“工资”。这使“试用期”“仲裁时效”等连续词能在 BM25 中匹配。

这是一种轻量教学实现。资料规模扩大或需要更精细的中文词法分析时，可以再替换为专门的分词器或检索引擎。

## 开关与参数

默认仍是原来的纯向量检索：

```powershell
python main.py
```

在当前 PowerShell 窗口启用混合检索：

```powershell
$env:HYBRID_RETRIEVAL = "true"
python main.py --profile
```

可选地设置 BM25 单路的候选数；未设置时与 `RETRIEVAL_K` 相同：

```powershell
$env:HYBRID_BM25_K = "8"
```

`--profile` 会分别显示 Chroma、BM25 和 Reranker 的耗时。

## 如何判断它有没有价值

对同一份不参与开发的保留题集，分别运行纯向量和混合检索，比较：

- 正确来源是否进入最终 `sources`；
- 必要事实是否出现在回答中；
- 无依据问题是否仍能正确拒答；
- 总耗时和各阶段耗时。

若混合检索没有提高来源命中，也没有修复具体漏检案例，就保持默认关闭，不把它当作自动优化。

## 首轮保留题集结果

在 `evals/heterogeneous_holdout_cases.json` 的 7 道固定题上，纯向量基线的正确来源命中为 7/7、必要事实命中为 7/7、正确拒答为 1/1。开启 BM25 后，对应结果为 6/7、6/7、1/1。

退化发生在“未按时足额发工资并申请仲裁”的混合题。BM25 新加入多段泛化的仲裁指南资料后，最终 Reranker 没有保留《劳动合同法》第三十条，回答因此遗漏“及时足额”。

结论是：当前的“直接合并全部候选”策略没有通过评测。功能保留为默认关闭的实验开关，不能作为现有检索链的默认优化。后续若继续研究，应先针对候选融合和 Reranker 的上下文预算提出新的可验证策略。
